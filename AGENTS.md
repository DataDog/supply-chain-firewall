# Repository guide

Supply Chain Firewall (`scfw`) is a Go command-line application that protects package-manager operations. It resolves the packages an npm, pip, Poetry, or uv command would install, asks the Datadog Code Security API to evaluate those packages, and then allows, warns about, or blocks the original command.

## Repository structure

- `scfw/main.go` is the executable entry point. Keep it limited to process-level setup and handing control to the CLI package.
- `scfw/internal/cli` defines Cobra commands and owns user-facing command orchestration: configuration, diagnostics, package-manager selection, policy outcomes, prompts, and running the approved command. Generic proxy configuration, registry-client cleanup, and lifecycle-context wiring stay in `cli/proxy.go`; `cli/registry.go` registers invocation-scoped ecosystem hook factories for each package manager; ecosystem-independent policy evaluation of resolved `pm.Package` values, decision caching, reporting, and presentation stay in `cli/proxy_evaluation.go`.
- `scfw/internal/build` owns build-time metadata such as the application version. Release builds inject these values through GoReleaser.
- `scfw/internal/ddapi` owns Datadog authentication, HTTP transport, and the Code Security API implementation of the `evaluation` interfaces (policy evaluation and run reporting). Package-manager-specific behavior does not belong here.
- `scfw/internal/evaluation` defines the policy evaluation and reporting domain: shared outcome/report types and the `Evaluator`/`Reporter` interfaces that the Datadog and local backends implement.
- `scfw/internal/evaluation/local` implements local evaluation (running the `verifier` package's verifiers) and local run reporting to a JSON Lines log file.
- `scfw/internal/verifier` defines the local package verification framework: the `Verifier` interface that concrete verifiers implement. Subpackages `verifier/osv` (OSV.dev advisories), `verifier/ddmalware` (Datadog malicious-software-packages-dataset), `verifier/age` (recently-published packages), and `verifier/list` (user-provided findings lists) each implement one verification source.
- `scfw/internal/proxy` owns the short-lived, loopback-only HTTP/HTTPS proxy that `scfw run` routes package manager traffic through, using goproxy's CONNECT interception with request-scoped response hooks and bounded body inspection before forwarding. File-backed response inspection and temporary-file cleanup live in `proxy/response_file.go`; response bytes remain withheld until inspection succeeds. It also owns generic proxied-command execution in `proxy/run.go` (child-only environment merging, streams, signals, job control, cleanup, and isolated invocation-scoped proxies for additional HTTP clients) and TLS material loading from explicit root pools, PEM files, or CA directories in `proxy/tls.go`; adapter-selected outbound routes in `proxy/transport_route.go` isolate connection pools and separate destination TLS from HTTPS-proxy TLS; adapters implement its `CommandConfigurer` interface. Its per-run certificate authority and interception certificates are generated with the Go standard library only. It is generic: ecosystem-specific request classification, metadata parsing, and package-manager-specific configuration do not belong here.
- `scfw/internal/home` resolves SCFW's home directory (`SCFW_HOME`, else a directory under the user's cache directory), where verification data is cached and the local log is written.
- `scfw/internal/ecosystem` exposes shared ecosystem identifiers through aliases, normalizes package names, and dispatches registry operations that are independent of a particular package-manager executable.
- `scfw/internal/ecosystem/npm` owns npm-registry source recognition and publication-data resolution for npm-compatible clients (npm, Yarn, pnpm, Bun). Its `NewProxyHook` constructor owns invocation-scoped classifier and packument-cache state and maps tarballs to `pm.Package` before invoking a caller-provided package policy callback. Every recognizable tarball is evaluated before forwarding, on any host; publication data comes from the full packument fetched with the caller's client, and response bodies are never inspected.
- `scfw/internal/ecosystem/common` defines shared ecosystem domain types and identifiers without importing concrete ecosystems, registry clients, or package-manager adapters. The shared `pm` package depends on these types rather than registry implementations.
- `scfw/internal/ecosystem/pypi` owns distribution request classification, JSON metadata observation and discovery, and publication-data resolution. Its `NewProxyHook` constructor owns invocation-scoped classifier, cache, and publication-resolution state and maps distributions to `pm.Package` before invoking a caller-provided package policy callback. Recognizable distribution filenames, including paths ending in slashes, are evaluated before forwarding; allowed requests retain bounded JSON metadata observation, deriving unknown project identities from validated JSON rather than distribution-shaped endpoint names. HTML and identified binary bodies normally stream without inspection, while observed JSON identifies exact advertised downloads and their publication dates. Managers can opt into MIME-independent archive-path inspection, which follows redirects and retains JSON metadata observation for archive-shaped endpoints. Opaque downloads are identified from bounded archive metadata inspection in `archive.go`, including streaming Zstandard decoding and compression-integrity validation, with response, cache, and range handling in `download.go`; archive entries are never extracted or executed.
- `scfw/internal/git` discovers local Git repository metadata and removes credentials before reporting.
- `scfw/internal/pm` owns the shared package and package-manager abstractions (including the `ProxyRunner` interface that embeds the core proxy's command-configuration contract), version handling, and reusable collections. Keep this package independent of concrete package managers.
- `scfw/internal/pm/internal/pythonproxy` provides read-only native macOS proxy discovery and urllib-compatible environment discovery and bypass matching; adapters retain their own routing precedence.
- `scfw/internal/pm/internal/gitproxy` owns bounded Git network snapshots, native URL/remote routing and TLS (including native CA defaults and outbound public-key pins), and child-only interception configuration; invocation-private HTTP helper overlays preserve named-remote context without modifying Git installations, while adapters retain other Git-client compatibility and precedence rules.
- `scfw/internal/pm/npm`, `scfw/internal/pm/pip`, and `scfw/internal/pm/poetry` each own integration with that executable: supported commands and versions, dry-run or temporary-project behavior, output parsing, and conversion into the shared `pm.Package` model. The pip adapter reads `[global]`, the active command section, and environment settings in Go (`settings.go`), extracts exact proxy-related flags and consumes value-taking global options, including unambiguous long abbreviations, to identify the first positional command without a command catalog (`arguments.go`), and returns PyPI classifier options from explicit source URLs (`classifier_options.go`). Literal pip TLS trusted-host matching stays in the adapter (`trust.go`) and is supplied through the core proxy’s `TrustURL` callback. Launcher/interpreter discovery (`interpreter.go`) uses launcher parsing first and cached, bounded pip diagnostics for shell shims. Native macOS proxy URLs and bypass rules are read through bounded, read-only `scutil --proxy` discovery (`system_proxy.go`) when proxy environment settings are absent. Requirements files and caches remain pip’s responsibility. The adapter always supplies process-only argument/environment overrides and explicit trust settings for pip/pip3; shared process execution and standard proxy environment/URL helpers belong to `proxy`. Native macOS discovery is shared through `pm/internal/pythonproxy`.
- `scfw/internal/pm/uv` owns uv/uvx command selection (including version updates and seeded virtual environments), read-only discovery of effective routing and registry settings, and child-only proxy and CA overrides, using `pm/internal/gitproxy` for scoped native Git settings and child overrides. When file-based proxy settings would override standard proxy variables, it supplies an invocation-scoped merged configuration beside the temporary CA; existing uv and project configuration, caches, environments, and lockfiles remain uv's responsibility. Configuration discovery follows physical directories and uv's workspace glob syntax; it opts into MIME-independent PyPI archive-path inspection without parsing uv's dependency inputs. Its `script.go` reads bounded local PEP 723 metadata, separates script inspection from directory/zipapp configuration discovery, and rejects inline proxies or script forms that cannot be inspected without changing execution. Its `tls.go` uses system trust by default and custom-only trust for explicit CA sources; `trust.go` handles string and structured host exceptions. Git uses a separate invocation-scoped proxy and CA with shared outbound routes so its trust settings cannot broaden registry trust.
- Tests live beside the code they cover as `*_test.go` files. Store registry payloads, package sources, configuration samples, and process scripts in the owning package’s `testdata` directory and read them from tests. Group related JSON responses as named cases in `responses.json` and uv TOML configuration samples as named tables in `configurations.toml` or `configurations.toml.tmpl`; keep templates and executable sources as separate files. Keep malformed inputs verbatim. `.tmpl` fixtures retain runtime substitutions for temporary URLs and paths. Add or update focused tests with every behavioral change. Common CLI proxy fixtures, TLS identities, upstream servers, and cleanup assertions live in `cli/proxy_helpers_test.go`.
- `.goreleaser.yml` is the authoritative cross-platform release-build configuration. Root-level files such as `go.mod`, `go.sum`, `Makefile`, and `.golangci.yml` define dependencies and development tooling.
- `.github` contains CI, release, and repository automation, with supporting scripts and their tests in `.github/scripts`; `images` contains documentation assets.

## Structure maintenance rule

Keep this guide accurate as part of every structural change. In the same change that creates, removes, renames, moves, or materially repurposes a package or top-level directory, update the structure section above to state its responsibility and boundaries. A new package must have one clear, cohesive responsibility, live at the narrowest appropriate scope, and avoid duplicating responsibilities already assigned here. If its purpose cannot be described in one concise sentence, reconsider the package boundary before adding it.

Preserve the existing separation of concerns: the CLI orchestrates (including evaluation-mode selection), `evaluation` provides shared evaluation/reporting abstractions, `ddapi` communicates with Datadog, `evaluation/local` and `verifier` implement local evaluation, `ecosystem` communicates with registries, `proxy` provides generic traffic interception, `pm` provides shared domain abstractions, and each `pm/<manager>` package implements one package-manager adapter. Do not put manager-specific parsing in `pm`, API transport in `cli`, or CLI presentation in lower-level packages.

Within a package, isolate ecosystem-specific behavior in explicitly named files (for example, `proxy_pypi.go`). Shared orchestration should select and wire ecosystem implementations without embedding their protocol logic. Ecosystem protocol handling belongs in the corresponding `ecosystem/<name>` package; policy orchestration, reporting, and presentation stay in `cli`.

## Validation

Run relevant unit tests while developing. Before considering any change complete, run both repository lint targets and resolve every reported issue:

```sh
make lint
make golangci-lint
```

Keep the local `golangci-lint` version aligned with the version used by CI. Do not skip linting because a change appears small or because focused tests pass.

The required build validation for every completed change is:

```sh
goreleaser build --snapshot --clean
```

Use this GoReleaser build rather than substituting `go build` or `make`; it validates the supported targets and the release-time flags defined in `.goreleaser.yml`.
